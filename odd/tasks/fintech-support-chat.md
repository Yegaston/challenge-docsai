# Fintech Support Chat

## Objective
Replace the one-shot entry path with a chat-first, synthetic-fintech transfer-support demonstration: bounded agent decisions, clarifying questions, read-only customer-scoped tool calls, and human escalation with shared conversation context.

## Why and scope
The existing ticket-analysis UI does not demonstrate tool calling or a conversational clarification loop. Preserve existing login, tickets, analyses, reports, and retention behavior during the additive rollout. One login endpoint serves server-assigned `customer` and `support` roles; no self-assigned roles. A shared support inbox shows escalated conversations only. Customer and human support see the same message history and can keep messaging after escalation; AI stops answering then. Never mutate financial state. Use synthetic transfer records only. Four elapsed hours after an unanswered agent clarification triggers automatic escalation; explicit 'I don't know' or request for support escalates immediately. Customer reply or resolution cancels pending escalation. Tool outputs are scoped server-side and reduced to safe activity summaries for the UI.

## Constraints and design assumptions
- No actual banking integration, money movement, PII collection beyond the existing demo account, or externally delivered notifications.
- Inactivity means four elapsed clock hours since a *persisted unanswered agent clarification*, not generic silence; repeat scheduling/late worker attempts may not create duplicate tickets.
- Preserve 90-day content eligibility/retention and owner isolation; support access requires a distinct account/role, and support cannot invoke tools under customer identity.
- Existing `.agents/` and `skills-lock.json` are untracked user files: leave untouched.
- Delivery strategy: feature/tracker branch chain, chosen by user. Branch `feat/fintech-support-chat` starts from `feat/part2-expiry` at `82d23ad`; no push/PR/merge authorized. Forecast and actual work exceed 400 authored changed lines; work-unit commits exist, PR slices are not packaged.
- Generated technical artifacts in English. Tests-first for deterministic behavior with observed RED/GREEN; unknown provider behavior tested with a fake adapter.

## Acceptance criteria
A customer can start a chat with a transfer-support question, receive an explicit clarification when evidence is insufficient, and get a status answer only after a server-authorized synthetic lookup. Every turn and safe tool event is visible on reload. Explicit inability/handoff or an unanswered clarification after four elapsed hours creates at most one linked support ticket. The customer and a separately authenticated support agent can read that conversation and exchange human messages, while the agent is inactive. Another customer cannot view it; no financial mutation is exposed. Existing ticket functionality remains operational.
