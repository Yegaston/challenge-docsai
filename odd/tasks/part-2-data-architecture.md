## Deletion and expiry design boundary

Owner deletion returns a conflict when that owner's analysis lock is held; the UI should explain that provider processing may continue and the user must retry. Do not cancel or claim to retract an already sent provider request. After a crash, an orphaned `running` row does not hold the session lock and may be deleted with its ticket. Use the same nonblocking lock for physical expiry: deny application reads/starts immediately at the 90-day cutoff, then skip busy owners for deletion and retry on the next bounded sweep. Apply ticket-and-analysis deletion in one database transaction, always owner-scoped; a failed query must not leave a partially deleted ticket. No deletion result promises immediate removal from backups or provider storage. This is an implementation assumption, not an independently approved legal policy.
